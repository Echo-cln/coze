# EvidenceOS

### 可追溯、可审计的智能分析报告工作台

[![CI](https://github.com/Echo-cln/coze/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Echo-cln/coze/actions/workflows/ci.yml) ![Status: Beta](https://img.shields.io/badge/status-beta-orange) ![TypeScript](https://img.shields.io/badge/TypeScript-5-blue)

**从多源材料到证据台账、冲突清单和可审计报告。**

EvidenceOS 是一个面向金融研究、政策汇报和咨询分析场景的报告工作台原型。它把材料解析、事实抽取、冲突识别、报告生成与交付串成一条可观察的流程，让报告中的关键判断尽可能回到来源和原文。

> **项目状态：Beta / 研究原型。** Web 工作台和 API 接入层已提交；真实解析与生成依赖单独部署的 Coze 工作流。未配置 C 模块时，只有未提交材料的空白工作台可进入明确标注的结构演示；提交材料会被阻断，避免固定样例冒充分析结果。当前仓库没有发布可复现的准确率基准，也没有包含可导入的 Coze 工作流定义。

## 为什么做 EvidenceOS

传统的“上传材料 → 让模型写报告”很难回答几个关键问题：

- 结论来自哪份材料、哪一页、哪段原文？
- 两份材料的数值不同，是统计范围不同，还是确实互相矛盾？
- 报告引用是否能回到证据台账，未解决的风险是否被清楚标出？

EvidenceOS 将**证据可追溯**与**冲突可解释**作为报告链路的核心约束。目标不是让文本看起来更长，而是让使用者能检查报告依据、发现资料缺口并判断哪些结论仍需人工核验。

## 核心能力

- **多源材料入口**：支持上传文件与在线来源；解析工作流返回来源清单和文本切片。
- **结构化事实台账**：围绕主体、指标、数值、单位、期间、范围、原文和定位组织证据。
- **分层冲突识别**：将硬规则检测与语义判断拆开，保留冲突所关联的证据。
- **流式任务反馈**：后端以 SSE 传递进度、证据、冲突、正文和最终结果。
- **行业化报告工作台**：提供金融投研、政务汇报和咨询调研模板配置，以及报告、证据地图、冲突雷达和质量视图。
- **审计包导出**：将报告正文、证据台账、冲突清单、来源状态和完整性检查结果打包为可下载 JSON。

```mermaid
    W -->|知识库检索词或文件| C
    C --> L["报告生成与引用校验"]
    L --> WF60["WF60 渲染与导出（可选）"]
    L --> R["报告、证据台账、冲突清单"]
```

### 你负责的模块：证据抽取与冲突检测

C 模块承接解析切片或知识库检索结果，产出可供报告生成使用的结构化证据与冲突结果。流程图中的职责边界如下：

1. **数据入口路由**：在文档切片与知识库检索结果之间选择输入路径，并汇入统一处理链路。
2. **文档切片**：将长材料整理为可处理片段。切片粒度、重叠策略以及页码/段落定位应以实际 Coze 节点配置为准。
3. **事实抽取**：从片段中提取事实，并绑定来源与原文。项目的数据契约还定义了主体、谓词、数值、单位、期间、范围、定位和置信度等字段。
4. **归一化与去重**：统一可比较字段并合并重复事实；去重时应保留各来源的出处，避免丢失证据链。
5. **硬冲突规则检测**：在主体、指标、期间和统计范围可比时，识别数值或口径差异。
6. **语义冲突判定**：补充规则难以覆盖的文本矛盾判断，并说明涉及的事实与判定理由。
7. **冲突合并与统计**：合并重复冲突，关联证据 ID，汇总类型和风险等级后输出。

**证据台账是模块输出的关键接口。** 每条事实应尽可能包含 `evidence_id`、`source_id`、`subject`、`predicate`、`value`、`unit`、`period`、`scope`、`quote`、`locator` 和 `confidence`。冲突清单应关联 `evidence_ids`，让用户可以从“存在差异”继续追到差异双方的原始依据。

> 上述流程节点来自项目中的工作流图与数据契约说明。具体提示词、规则阈值、模型配置和节点级评测尚未随仓库发布；README 不将这些未公开配置表述为已经验证的实现细节。

### 面试讲解：项目是什么

**EvidenceOS 是一套“先整理证据，再生成报告”的智能分析工作台。**它面向金融投研、政策汇报和咨询调研，把用户材料经过解析、事实抽取、口径整理、差异识别，再组织成带来源引用的报告。项目关注的不只是生成文本，还包括让使用者能够追问“这句话来自哪里、原文是什么、差异为什么存在”。

可以把系统拆成三层：

| 层次 | 职责 | 仓库中的位置 |
|---|---|---|
| 交互与任务层 | 上传材料、设置问题和参数、查看进度与结果 | Next.js 页面和组件 |
| 服务编排层 | 调用工作流、转换 SSE 事件、校验输出、生成审计包 | `src/app/api/report/` |
| 证据与报告层 | 解析材料、抽取结构化证据、识别差异、撰写报告 | 外部 Coze 工作流：WF10 / C 模块 / WF60 |

WF10 负责材料解析；C 模块负责证据抽取与冲突检测；报告生成由服务端生成链路承担，WF60 可作为渲染与导出增强。工作流通过独立的 HTTP/SSE 接口接入，Web 应用负责任务编排和结果呈现。

### 面试讲解：我负责什么

根据目前项目分工，我负责 **C 模块：证据抽取与冲突检测**，重点是让“材料里的说法”变成可追溯、可比较的结构化记录，而不是让模型直接从整篇文档跳到结论。

- **证据抽取：** 将一条事实整理为主体、指标、数值、单位、期间、统计范围、来源、原文引用和页码/章节定位等字段。
- **规范化与去重：** 统一可比较字段，合并重复事实时保留各来源出处；遇到主体、期间或口径不同的内容时不贸然合并。
- **冲突识别：** 先判断两条证据是否可比，再处理数值差异或文本矛盾。数值比较至少要核对主体、指标、单位、期间和统计范围；口径不同的证据应分别保留并解释差异。
- **冲突输出：** 将冲突关联到证据 ID，给出类型、风险级别、解释和处理状态，让报告、冲突视图和证据台账使用同一条证据链。

这些职责来自项目工作流图与数据契约。**Coze 工作流定义、节点提示词、参数和标注评测集尚未随 GitHub 仓库发布**；面试时应把你能展示的工作流配置、实际节点和实验记录作为实现证据，不要把设计文档中的建议说成已经验证的效果。

### 60 秒项目介绍

> 我参与开发了 EvidenceOS，一个面向金融投研、政策汇报和咨询调研的可追溯报告工作台。传统的“把材料直接交给大模型写报告”很难核对结论来源，也容易把统计口径不同的数据误判成冲突。项目把流程拆成材料解析、结构化证据抽取、差异识别和报告生成，并通过证据 ID、原文引用和页码或章节定位把报告结论连回材料。
>
> 我负责 C 模块的证据抽取与冲突检测，重点设计证据字段、规范化和去重边界，以及数值和语义差异的处理流程。比如比较两个数值前，先确认主体、指标、期间和口径一致；如果统计范围不同，就保留两条证据并解释差异，而不直接混算。仓库中的 Next.js 服务负责工作流接口、SSE 进度和审计包；Coze 工作流本身是独立部署的。当前我们补上了来源、引用覆盖率和占位内容等结构校验，但还没有公开标注评测集，因此不会把结构检查说成事实准确率或模型效果。

### 面试追问：建议这样回答

**为什么不直接让大模型读完材料后写报告？**  
直接生成很难稳定追溯每条结论的原文依据，也不方便区分口径差异和真实矛盾。我们先抽取原子证据并保留来源、原文和定位，再让报告引用证据 ID；这样至少能检查报告是否引用了已有证据，并把人工核验落到具体材料位置。

**两组数据不一致时，怎么判断是不是冲突？**  
先比较主体、指标、单位、期间和统计范围。只有这些维度兼容，才进一步判断数值是否存在实质差异；如果一条是全渠道口径、另一条是上市业务口径，应标为口径差异并保留两条原始证据，而不能直接拿两个数做百分比差异计算。语义冲突需要结合原文解释，不能只看数字。

**怎么证明模块效果好？**  
目前不能用“报告看起来完整”证明抽取或冲突检测准确。下一步应建立人工标注样本，分别评估证据抽取的准确率/召回率、重复合并正确率、冲突识别的精确率/召回率，以及报告引用是否真正被原文支持。仓库当前的引用覆盖率和章节检查属于结构指标，不等于语义正确率；项目尚无公开基准结果。

**你具体实现了什么，哪些是系统的整体能力？**  
先明确个人负责的 C 模块边界，再展示对应的 Coze 节点、输入输出字段、冲突样例和你参与的配置或代码。Next.js 工作台与 API 接入层是仓库中的系统能力；WF10、C 模块和 WF60 是外部工作流。回答时应区分个人贡献、团队成果和外部服务，不能把整个系统都说成自己独立完成。

- Node.js 22 或更高版本（pnpm 11 要求）
- pnpm 11.25

### 启动

```bash
git clone https://github.com/Echo-cln/coze.git
cd coze
npm install --global pnpm@11.25.0
pnpm install --frozen-lockfile
pnpm dev
```

首次运行前，从模板创建本地环境文件：

```powershell

```

运行安全回归：

```bash

```

## API 与事件流

| 路由 | 作用 |
|---|---|
| `POST /api/report/parse` | 调用 WF10 解析文件和 URL，返回来源与解析切片 |
| `POST /api/report/generate` | 调用 C 模块，生成证据、冲突和报告结果 |
| `POST /api/report/audit-pack` | 将当前任务结果生成可下载的 JSON 审计包 |

生成接口执行确定性完整性检查：验证引用编号、证据与来源映射、解析来源状态、必备章节、占位字段和正文引用覆盖率。严格模式下，核心分析问题缺失、来源清单缺失、证据无法映射到来源、引用了解析失败来源、占位字段、未解决高风险冲突或事实段落引用覆盖率低于 50% 时会阻断报告交付。检查不代表事实正确率或模型效果基准；引用覆盖率也只是结构指标，仍需人工核对原文。主要事件为 `progress`、`evidence`、`conflict`、`content`、`metrics`、`done` 和 `error`。具体输入和输出字段以 `src/app/api/report/` 下的路由实现与工作流契约为准。

## 安全与部署边界

这个仓库包含服务端 API 和外部工作流凭证配置。真实链路上线时，请把应用放在公司 SSO、身份认证网关或可信访问代理之后；当前仓库没有内置用户认证、租户隔离、持久化任务授权或跨实例限流，不能把配置了真实 Token 的公开实例直接暴露到互联网。

目前已落实的基础防护包括：

- 报告预览先转义文本，只允许 HTTP/HTTPS 和页内锚点链接，避免模型输出把脚本注入工作台。
- API 限制 JSON 请求体为 8 MB；上传最多 20 个文件、单文件 20 MB、合计 100 MB，并校验允许的扩展名。
- 在线来源仅接受公网 HTTP/HTTPS 地址，并拒绝常见私网、回环和本机地址；工作流服务也应配置出站网络限制，抵御 DNS 解析变化和工作流侧 SSRF。
- 对外请求设有超时；错误响应不回传上游服务正文；导出接口限制请求大小并禁用缓存。
- 移除通配远程图片主机，并添加基础安全响应头。

依赖扫描使用 npm 官方审计源；本次锁文件审计结果为 **0 条已知漏洞**。审计数据库会变化，升级依赖后应重新运行 `pnpm audit`。自动化检查不等同于渗透测试，也不能证明 Coze 工作流、对象存储策略或部署网络配置安全。部署前应单独验证身份认证、存储桶访问权限、签名 URL 有效期、工作流出站访问规则与日志脱敏。不要上传真实敏感材料进行公开演示。
